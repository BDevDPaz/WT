A continuación entrego la tabla formal de transiciones en formato de especificación, completa, y separada en cuatro dominios operativos:
1. Transiciones de jornada / sesión
2. Transiciones de sistema
3. Transiciones de reportes
4. Transiciones de seguridad y feedback
La tabla está construida como modelo canónico propuesto, pero anclado estrictamente en los comportamientos y estados que sí existen hoy en tus archivos analizados: estados de work_sessions, geocerca, background task, auditoría, settings, feedback, UI state y mocks detectados. 123456

───

1) Convención formal de cada transición
Cada transición se define con esta estructura:
• Evento
• Origen
• Precondiciones
• Mutación canónica
• Side-effects del sistema
• Derivaciones afectadas
• Estado operacional visible resultante (engineState)
El engineState visible de UI se trata aquí como derivación, no como verdad primaria persistida, porque en el sistema actual los estados persistidos reales viven en work_sessions.status, mientras que la UI usa EngineState como simulación visual. 156

6) Tabla de resolución del engineState derivado
Esta tabla no es un evento; es la regla de lectura que convierte el estado canónico en el estado operativo visible que hoy consume la UI. La base observable para esta tabla ya existe en work_sessions.status, EXIT_TIMESTAMP, los estados mock de index.tsx y el EngineState declarado en OperationalHeroCard.tsx. 1256
R-01 — NO_INICIADA
Se resuelve cuando activeSessionId = null y no existe sesión abierta válida. 15
R-02 — ESPERANDO_LLEGADA
Se resuelve cuando existe sesión activa y domainStatus = pending_arrival, con geocerca monitoreando o esperando check-in. 216
R-03 — EN_TRASLADO
Se resuelve cuando existe sesión activa y domainStatus = travel. 236
R-04 — ACTIVA
Se resuelve cuando existe sesión activa y domainStatus = active, sin salida pendiente abierta. 216
R-05 — SALIDA_DETECTADA
Se resuelve cuando domainStatus = active y runtime.geofence.lastExitTimestampMs tiene valor válido todavía no consumido por auto checkout ni restaurado manualmente. 26
R-06 — CERRADA
Se resuelve cuando la sesión operativa actual fue marcada completed o cuando ya no existe sesión activa tras un cierre formal. 15
R-07 — ASINCRONIA_CHECKIN
Se resuelve como estado derivado de anomalía, no persistido, cuando el sistema espera llegada pero detecta inconsistencia operativa de GPS / sincronía. La UI lo modela explícitamente y SystemHealthBlock ya distingue estados degradados, pero el backend actual aún no persiste esta anomalía como campo dedicado. Por eso aquí queda formalizado como derivación del sistema, no como columna persistida. 562
R-08 — NO_SHOW
Se resuelve como estado derivado de excepción operacional cuando una sesión esperada de llegada falla y debe ser abortada o forzada manualmente. La UI lo modela explícitamente, pero el backend actual no lo persiste como status en DB; por eso también queda en la capa derivada, no en la primaria. 561

7) Regla de consistencia del sistema
La tabla completa queda gobernada por esta regla:
Ningún evento muta directamente engineState; cada evento muta estado canónico primario (domain o runtime) y después las derivaciones recalculan el engineState, el SystemHealth, los badges de integridad, el historial visible y el feedback UX.12346
